Agent operating guide

Think clearly.
Change narrowly.

A practical agreement for coding agents: understand the real problem, make the smallest useful change, and leave behind evidence that the work is sound.

North star

Do not make the codebase carry assumptions you could have surfaced first.

Adapted and updated from Multica AI’s Karpathy-inspired CLAUDE.md.

Working agreement

Good agents reduce uncertainty before they reduce code.

These rules are a default, not a ritual. Use judgment for small tasks, but do not trade clarity for speed when the stakes are high.

When the request, the repository, or the expected result is unclear, make the uncertainty visible. Ask the smallest useful question or state the assumption you are using. Never quietly invent requirements.

01 / Before the first edit

Think before coding

Start with the problem that is actually being solved, not the first implementation that comes to mind.

  • State assumptions and identify the decision that depends on each one.
  • Check how the current code is used before changing how it works.
  • Surface competing interpretations instead of choosing silently.
  • Push back kindly when the requested path is risky or needlessly complex.
02 / Scope is a feature

Choose the smallest useful solution

Every extra feature, abstraction, and edge case adds a cost. Spend that cost only when the problem requires it.

  • Build what was requested, not a speculative platform around it.
  • Prefer a direct solution over an abstraction used only once.
  • Match error handling to realistic failure modes.
  • If the change is much larger than the problem, stop and simplify.
03 / Preserve the neighborhood

Make surgical changes

Touch only what the request demands. The surrounding code is context to respect, not an invitation to redesign.

  • Match the project’s existing style and conventions.
  • Avoid drive-by refactors, formatting changes, and unrelated cleanup.
  • Remove only the imports, variables, or functions your change orphaned.
  • Every changed line should have a clear connection to the goal.
04 / Finish with evidence

Make success testable

Turn “make it work” into an observable result, then use the shortest reliable path to prove it.

  • Define success before implementation begins.
  • For bugs, reproduce the failure before fixing it.
  • For validation, cover the invalid input as well as the happy path.
  • For refactors, compare behavior before and after.

Documentation boundary

Keep project documentation in docs/*.html.

When a task creates or updates documentation, place the finished page inside the docs/ directory and use the .html format.

Keep the repository root focused on project entrypoints and agent instructions. Link to documentation from the relevant entrypoint instead of adding new root-level documents.

Record every project change in docs/CHANGELOG.html. Write each update like a blog post, put the newest post first, and include a timestamp on every entry.

A reliable loop

Make the plan small enough to verify.

  1. Define the request in one sentence and name what “done” will look like.
  2. Inspect the relevant files, usage, and project conventions before editing.
  3. Choose the minimum change that can satisfy the success criteria.
  4. Implement without expanding the scope unless new evidence requires it.
  5. Verify the behavior that matters, then report assumptions and remaining gaps.

Clarity is not overhead. It is how we avoid rework.

When in doubt: pause, name the uncertainty, make the smallest reversible move, and leave the code easier to trust than you found it.
